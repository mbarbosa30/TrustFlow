Advogato was a pioneering online community platform launched in 1999 by Raph Levien, specifically tailored for free and open-source software (FOSS) developers. It functioned as a social network where users could publish diaries, articles, and project updates, but its standout feature was a sophisticated trust metric system designed to identify and rank "the best" developers based on peer certifications (vouches). The platform emphasized attack resistance against spam, Sybils, or manipulation, using graph theory to propagate trust from a small set of "seed" developers. Advogato operated until around 2017, but its trust model remains influential in reputation systems (e.g., influencing modern blockchain DAOs or contributor scoring in GitHub-like platforms).

The trust metric was the core innovation, using the **max-flow min-cut theorem** from graph theory to compute a "group trust" score. This wasn't individual reputation ranking but a way to determine who was "trusted" within the community, with tiers that effectively highlighted the elite (Masters) as the "best" developers. It was explicitly designed to be secure against adversarial attacks, sacrificing some intuitiveness for robustness.

### The Trust Metric: Group-Level Trust Propagation
Advogato modeled the community as a directed graph:
- **Nodes**: Developers (users).
- **Edges**: Certifications (vouches) from one user to another, at levels like Apprentice (low trust), Journeyer, or Master (high trust). Capacities on edges were based on the certification level (e.g., higher level = higher capacity, often unit or decayed).
- **Seeds**: A small, fixed set of highly trusted "master" developers (e.g., initial 4-6 FOSS legends like Linus Torvalds or Richard Stallman types—hardcoded for bootstrapping).
- **Source and Supersink**: Artificial nodes for flow computation.

The metric computed "group trust" rather than per-user scores, determining who was "accepted" into trusted tiers. This identified "best" developers as those with strong, verified chains of vouches from seeds.

#### Key Design Choices
- **Attack Resistance as Priority**: The system sacrificed monotonicity (adding vouches might not always increase trust) for security—fakes couldn't infiltrate without saturating the min-cut (expensive in effort/vouches).
- **Tiers via Thresholds**: Ran the algorithm multiple times with increasing edge capacity thresholds (e.g., low for Apprentice, high for Master) to create ranks.

| Tier | Description | Flow Threshold | Typical % of Users |
|------|-------------|---------------|-------------------|
| Observer | No vouches needed | N/A | Entry-level, post diaries only |
| Apprentice | Basic trust | ≥1.0 on low-cap edges | ~40% (new contributors) |
| Journeyer | Moderate trust | ≥1.0 on medium-cap edges | ~40% (active devs) |
| Master | High trust | ≥1.0 on high-cap edges | ~20% (elite, "best" devs) |

### The Max-Flow Min-Cut Algorithm in Advogato
The algorithm models trust as a flow network, using Ford-Fulkerson (or Edmonds-Karp variant) to compute maximum flow from source to supersink. The min-cut (equal to max-flow by theorem) determines the "bottleneck" of trust, ensuring only robust paths count.

1. **Graph Construction (Node-Splitting for Capacities)**:
   - Split each node into "in" and "out" (to enforce per-node caps).
   - Source → seed_in (∞ capacity for seeds).
   - Seed_in → seed_out (capacity =1.0 or level-based).
   - Outgoing edges: endorser_out → endorsee_in (capacity based on certification level, e.g., Master vouch = higher cap).
   - All node_out → supersink (unit 1.0 cap—each accepts 1 unit trust).

2. **Max-Flow Computation**:
   - Run Edmonds-Karp (BFS for augmenting paths) from source to supersink.
   - Flow = conserved "trust" pushed through network until no paths left.
   - Example: With 2 seeds vouching you directly (cap=1.0 each), flow=2.0 if paths saturate; min-cut=2.0 (cut the 2 edges to you).

3. **Min-Cut Interpretation**:
   - Min-cut = smallest capacity set disconnecting source from supersink.
   - Trusted if flow to your node_out (before supersink) ≥1.0—means at least 1 unit trust reaches you through robust paths.

4. **Multi-Tier Ranking**:
   - Run algorithm 3 times with filtered edges (low-cap for Apprentice, high for Master).
   - Highest tier you achieve = rank (e.g., Master = "best" developer, with privileges like editing projects or vouching others).

#### How It Was Used to Find "Best" Open-Source Developers
Advogato's metric surfaced "best" developers via collective peer validation, not self-reported metrics (e.g., commits). It identified elites as those with high-flow paths from seeds:
- **Ranking Mechanism**: Masters (high-flow, strong min-cut) formed the "core" (small ~10-20% of users)—they had broad, verified endorsements from other Masters/Journeyers, mirroring FOSS collaboration (e.g., kernel maintainers vouching contributors).
- **"Best" Criteria**: High tier = "best" (e.g., Masters like Miguel de Icaza or Alan Cox were early examples). The system skewed to a power-law distribution (few Masters, many Apprentices), ensuring "best" rose through chains of reputable peers.
- **Practical Use**: Only trusted tiers could post articles or moderate—reducing spam, highlighting Masters' content as "best." Experimental data (Advogato archive) showed ~1,000 active nodes with ~200 Masters—aligning with Pareto (80/20) in open-source (few core contributors).
- **Advantages Over Alternatives**: Unlike star-counts or commit-based (e.g., GitHub), it was attack-proof (min-cut required real capacity) and group-focused (identified "trusted community" vs. individuals).
